# 数据权限重构：支持大数据量枚举值方案

## 1. 背景与目标

当前 `AclManager.injectRowAclFilterToConfig` 会把用户行级数据权限值合并到 `QueryConfigure.filter.fields` 中，最终由 `DefaultDataSourceSqlBuilder.buildExactWhereSql` 按普通筛选条件生成：

```sql
门店ID in ('1', '2', 'xx', ...)
```

当门店 ID 枚举值达到 10 万+时，即使 `buildExactWhereSql` 已按 1000 个值拆分多个 `IN`，整条 SQL 仍可能超过 Doris 可执行 SQL 长度，也会增加 SQL 解析、优化和传输成本。

本次重构目标：行级数据权限支持按字段配置选择过滤方式。只有字段编码命中系统配置 `ssm.data.auth.filter.by.exists.field.codes` 时，才改为 `exists` 半连接过滤；未命中配置的字段继续沿用当前 `QueryField.values` 合并和 `IN` 拼接逻辑。用户前端普通筛选仍保持原有 `IN`、范围、模糊匹配等逻辑。

## 2. 推荐方案：字段标识控制 exists

### 2.1 核心思路

通过 `SC` 系统配置控制哪些字段走 `exists`：

```java
String existsFilterFieldCodes = SC.v("ssm.data.auth.filter.by.exists.field.codes", "");
```

配置值使用字段编码列表，例如：

```properties
ssm.data.auth.filter.by.exists.field.codes=STORE_ID,SHOP_ID
```

查询构建时按字段配置分流：

- 字段编码命中 `ssm.data.auth.filter.by.exists.field.codes`：不把权限枚举值写入 `QueryField.values`，改为在查询 SQL 的 `where` 中追加权限存在性判断。
- 字段编码未命中配置：完全沿用当前逻辑，将权限值合并到 `QueryField.values`，后续由 `buildExactWhereSql` 生成 `IN`。

命中 `exists` 配置后的 SQL 形式：

```sql
exists (
    select 1
    from ssm_data_auth_exists_filter acl
    where acl.user_name = '${userName}'
      and acl.field_code = '${fieldCode}'
      and acl.dim_code = '${dimCode}'
      and acl.item_code = <查询模型中的权限字段>
)
```

对“门店 ID”权限来说，最终效果是：

```sql
exists (
    select 1
    from ssm_data_auth_exists_filter acl
    where acl.user_name = '${userName}'
      and acl.field_code = 'STORE_ID'
      and acl.item_code = fact_table_alias.store_id
)
```

这样 SQL 长度与用户拥有多少门店权限无关，只与管控字段数量有关。

### 2.2 授权状态判定

字段命中 `exists` 配置后，不能简单用“权限明细表是否有记录”判断是否有权限。字段仍需要遵守现有数据权限模式：

| 场景 | 判定结果 | SQL 行为 |
| --- | --- | --- |
| 用户有 `-9999` 全部权限 | 全量权限 | 不追加 `exists` |
| 用户没有配置该字段权限，且字段 `dataAuthMode = no_cfg_all` | 默认全量权限 | 不追加 `exists` |
| 用户有部分枚举权限 | 部分权限 | 追加 `exists` |
| 用户没有配置该字段权限，且字段 `dataAuthMode = no_cfg_none` | 无权限 | 追加 `1 = 0` |

关键点：`no_cfg_all` 表示“未配置有权限”。例如某用户没有配置“门店 ID”的数据行级权限，但该字段权限模式是 `no_cfg_all`，他默认拥有所有门店权限。此时如果前端筛选门店 ID，只应保留前端筛选条件，不应该追加 `exists`，否则由于权限明细表没有该用户门店记录，会导致查不到任何数据。

### 2.3 适用范围

`exists` 只用于系统配置明确指定的大数据量枚举权限字段，典型场景是“门店 ID”这类用户权限值可能达到 10 万+的字段。

不建议默认全量切换，原因：

- 现有小枚举权限字段使用 `IN` 更直观，改动面更小。
- 部分定制逻辑依赖 `QueryField.values`，例如城市权限兼容 DMG 的逻辑，贸然切换可能改变行为。
- 配置开关可以灰度发布，先对门店 ID 生效，验证稳定后再扩展到其他大枚举字段。
- 配置开关只决定“有部分权限时使用哪种 SQL 过滤方式”，不改变 `no_cfg_all`、`no_cfg_none` 的授权语义。

### 2.4 权限明细表

需要提供一张 Doris 查询侧可访问的权限明细表，建议命名为 `ssm_data_auth_exists_filter`。如果 `bi_portal.sys_data_auth` 只在 MySQL，需要通过同步任务或离线任务同步到 Doris。

建议字段：

| 字段 | 说明 |
| --- | --- |
| `user_name` | 生效用户，角色、部门权限展开后的最终用户 |
| `field_code` | SSM 元字段编码，例如门店 ID 字段 code |
| `module_code` | 权限模块，行级权限为 `ssm_row` |
| `dim_code` | 权限维度编码 |
| `item_code` | 权限枚举值，例如门店 ID |
| `item_value` | 权限枚举展示值，可选 |
| `auth_source` | 权限来源：User、Role、Dept，可选 |
| `expire_time` | 权限失效时间或同步后的有效期字段 |
| `dt` / `update_time` | 分区或同步时间 |

建议按 `user_name`、`field_code`、`item_code` 建索引、分桶或排序键，保证 `exists` 查询能快速定位权限集合。

## 3. 改造计划

### 3.1 `AclManager`

涉及类：`java/cn/bi_queryer/bi/ssm/engine/acl/AclManager.java`

修改方法：`injectRowAclFilterToConfig`

修改逻辑：

- 保留识别模型中哪些字段需要行级数据权限管控的逻辑，包括 `dataAuthDimCode`、`aclMetaFields`、`allModelMetaFields` 的判断。
- 新增字段过滤模式判断：通过 `SC.v("ssm.data.auth.filter.by.exists.field.codes", "")` 获取走 `exists` 的字段编码列表，只有当前权限字段编码命中该列表时，才进入 `exists` 权限过滤分支。
- `exists` 分支不再把用户权限明细逐条转换成 `FieldValue` 并写入 `QueryField.values`。
- `exists` 分支先判断字段授权状态：全量权限、部分权限、无权限。
- 全量权限包括两类：用户显式拥有 `BIConsts.Ssm_Row_Acl_All_Dim_Value`，或字段 `dataAuthMode = no_cfg_all` 且用户未配置该字段权限。
- 对部分权限字段，构造一个行权限过滤描述对象，写入 `QueryContext`，而不是写入 `config.getFilter().getFields()`。
- 默认分支保持当前逻辑：继续构造 `QueryField`、填充 `FieldValue`、与前端筛选值取交集，并追加到 `config.getFilter().getFields()`。
- 对开启 `exists` 的字段，如果判定为全量权限，不生成权限过滤，前端筛选门店 ID 时仍只走前端筛选条件。
- 对开启 `exists` 的字段，如果判定为无权限，生成一个“无权限”过滤描述，后续 SQL builder 直接生成 `1 = 0`。
- 对未开启 `exists` 的字段，无权限处理保持当前 `null` 哨兵值逻辑。

修改原因：

- 大枚举字段不适合继续通过 `QueryField.values` 承载 10 万+权限值。
- 小枚举字段没有必要切换为 `exists`，保留当前逻辑可以降低回归风险。
- 系统配置能让门店 ID 先灰度改造，不影响其他行级权限字段。

### 3.2 系统配置

涉及配置：`ssm.data.auth.filter.by.exists.field.codes`

配置示例：

```properties
ssm.data.auth.filter.by.exists.field.codes=STORE_ID,SHOP_ID
```

读取方式：

```java
String existsFilterFieldCodes = SC.v("ssm.data.auth.filter.by.exists.field.codes", "");
```

修改原因：

- 过滤模式由运行时配置控制，可以不改元数据表结构。
- 支持按环境、按发布节奏灰度开启门店 ID 等大枚举字段。
- 避免把所有行级权限字段都强制切换到 `exists`。

### 3.3 `QueryContext`

涉及类：`java/cn/bi_queryer/bi/ssm/engine/QueryContext.java`

新增内容：

- 新增行级权限过滤列表，例如：

```java
private List<DataAuthExistsFilter> dataAuthExistsFilters = new ArrayList<>();
```

- `clone()` 中复制 `dataAuthExistsFilters`。
- 增加 getter、setter、add 方法。

建议新增模型类：

`java/cn/bi_queryer/bi/ssm/engine/acl/DataAuthExistsFilter.java`

字段建议：

```java
private String fieldCode;
private String dimCode;
private String moduleCode;
private String dataAuthMode;
private String tableId;
private String tableAlias;
private String fieldName;
private boolean denyAll;
private boolean allAuth;
```

修改原因：

- SQL builder 需要知道“哪个查询字段要被权限表过滤”，以及该字段在最终 SQL 中的表别名和真实列名。
- `dataAuthMode` 用于区分“未配置默认全部”和“未配置无权限”，避免 `no_cfg_all` 用户被错误追加 `exists`。
- 使用强类型对象比把运行时过滤描述塞进 `QueryField.ext` 更清晰，也能减少普通筛选和行权限之间的耦合。

### 3.4 `DefaultDataSourceSqlBuilder`

涉及类：`java/cn/bi_queryer/bi/ssm/engine/DefaultDataSourceSqlBuilder.java`

修改方法：

- `buildWhereSqlFragments`
- 新增 `buildRowAclWhereSqlFragments`
- 新增 `buildRowAclExistsSql`

修改逻辑：

- 保留现有普通筛选逻辑，`buildExactWhereSql` 不再承担行级权限大集合处理。
- 在普通筛选 SQL 片段构造完成后，读取 `cxt.getDataAuthExistsFilters()`，追加行级权限 SQL 片段。
- 对 `denyAll = true` 的权限过滤，追加：

```sql
1 = 0
```

- 对正常权限过滤，追加：

```sql
exists (
    select 1
    from ssm_data_auth_exists_filter acl
    where acl.user_name = '${userName}'
      and acl.module_code = 'ssm_row'
      and acl.field_code = '${fieldCode}'
      and acl.dim_code = '${dimCode}'
      and acl.item_code = ${tableAlias}.${fieldName}
)
```

- 如果字段大小写不敏感或字段类型需要转换，沿用 `getWhereFieldFullName(field)` 的处理结果，避免权限字段与普通筛选字段 SQL 表达式不一致。

修改原因：

- 字段编码命中 `exists` 配置的行级权限需要作为强制 `where` 条件追加。
- 字段编码未命中配置的行级权限继续走当前普通过滤 SQL 构造逻辑，保证兼容。
- 使用 `exists` 可以让大枚举权限字段的 SQL 长度保持稳定，Doris 优化器也可以按半连接方式执行。

### 3.5 `SSDQueryService` 与 MyBatis

涉及类：

- `java/cn/bi_queryer/bi/ssm/query/SSDQueryService.java`
- `resources/mybatis/mapper/ssm/ssd.query.ibatis.xml`

修改逻辑：

- `getDataAuthByUser` 当前仍可用于判断“是否有全部权限”和兼容现有页面展示。
- 新增一个只查询权限概要的方法，例如 `getRowAclSummaryByUser(userName)`，返回用户在每个 `fieldCode + dimCode` 下的授权状态：`allAuth`、`partialAuth`、`denyAll`，并返回字段 `authMode`。
- `AclManager` 只对字段编码命中 `exists` 配置的字段使用概要查询结果，避免加载 10 万+权限明细。
- 字段编码未命中配置的字段继续复用当前 `getDataAuthByUser` 明细结果，保证原逻辑不变。
- 概要查询必须保留现有 `DataAuthMode.no_cfg_all` 语义：字段未配置权限明细且 `authMode = no_cfg_all` 时返回 `allAuth = true`。

修改原因：

- 大枚举字段如果继续通过 `getDataAuthByUser` 返回明细，会造成 Java 内存和网络传输压力。
- 对字段编码命中 `exists` 配置的字段，最终 SQL 已通过 Doris 权限表过滤，Java 侧只需要知道是否全量授权、是否无权限、需要过滤哪些字段。
- 对字段编码未命中配置的字段，保留当前明细查询，避免影响既有功能。
- 如果概要查询不处理 `no_cfg_all`，会把“未配置默认全部”误判为“无权限”，导致追加 `1 = 0` 或无效 `exists`。

### 3.6 配置发布

涉及位置：

- 系统配置中心：新增或维护 `ssm.data.auth.filter.by.exists.field.codes`。
- 配置值：逗号分隔字段编码，例如 `STORE_ID,SHOP_ID`。
- 配置默认值：空字符串，表示所有字段都沿用当前 `IN` 过滤逻辑。

修改原因：

- `exists` 必须由字段编码显式命中配置触发。
- 默认关闭可以避免上线后所有行级权限字段行为同时变化。
- 通过配置发布可以快速回滚某个字段的 `exists` 过滤方式。

### 3.7 权限数据同步任务

涉及位置：根据现有 ETL 或同步任务模块落地。

改造逻辑：

- 将 `bi_portal.sys_data_auth` 中 User、Role、Dept 权限展开为用户粒度。
- 只同步 `module_code = 'ssm_row'` 的行级权限。
- 过滤已过期权限，或同步 `expire_time` 并在 `exists` 中追加有效期判断。
- 写入 Doris 表 `ssm_data_auth_exists_filter`。

修改原因：

- 查询 SQL 在 Doris 执行，权限表也必须在 Doris 可访问。
- 提前展开角色和部门权限，可以让查询时只按 `user_name` 过滤，避免每次查询都执行复杂组织关系逻辑。

## 4. 用户筛选与数据权限的关系

用户前端筛选继续走原逻辑，例如：

```sql
fact.store_id in ('1001', '1002')
```

行级权限额外追加：

```sql
exists (
    select 1
    from ssm_data_auth_exists_filter acl
    where acl.user_name = 'zhangsan'
      and acl.field_code = 'STORE_ID'
      and acl.item_code = fact.store_id
)
```

当字段编码命中 `exists` 配置时，两者同时存在，SQL 自然表达为：

```sql
用户筛选条件 AND 数据权限条件
```

即最终结果为“用户筛选集合 ∩ 用户有权限集合”。不需要在 Java 内存中计算两个集合交集。

当字段编码未命中 `exists` 配置时，仍按当前逻辑在 Java 侧把权限值与用户筛选值合并后生成普通过滤条件。

### 4.1 未配置默认全部的门店筛选 case

用户 A 没有配置“门店 ID”的数据行级权限，字段配置为：

```text
dataAuthMode = no_cfg_all
ssm.data.auth.filter.by.exists.field.codes 包含门店 ID 字段编码
```

用户 A 在前端筛选门店：

```sql
fact.store_id in ('1001', '1002')
```

正确 SQL 行为：

```sql
where fact.store_id in ('1001', '1002')
```

错误 SQL 行为：

```sql
where fact.store_id in ('1001', '1002')
  and exists (
      select 1
      from ssm_data_auth_exists_filter acl
      where acl.user_name = 'userA'
        and acl.field_code = 'STORE_ID'
        and acl.item_code = fact.store_id
  )
```

错误原因是：用户 A 默认拥有所有门店权限，权限明细表中没有他的门店明细记录；追加 `exists` 会把结果错误过滤为空。

## 5. 测试计划

- 字段编码未命中 `exists` 配置：继续生成当前 `IN` 权限过滤，结果与当前逻辑一致。
- 字段编码命中 `exists` 配置且用户有全部权限：不追加 `exists`，结果与当前逻辑一致。
- 字段编码命中 `exists` 配置、用户未配置权限、字段 `dataAuthMode = no_cfg_all`：不追加 `exists`，前端门店筛选正常生效。
- 字段编码命中 `exists` 配置、用户未配置权限、字段 `dataAuthMode = no_cfg_none`：SQL 追加 `1 = 0`，返回空结果。
- 字段编码命中 `exists` 配置且用户有部分门店权限：SQL 包含 `exists`，不包含权限门店 ID 的长 `IN`。
- 字段编码命中 `exists` 配置且用户有 10 万+门店权限：SQL 长度保持稳定，Doris 可执行。
- 字段编码命中 `exists` 配置且用户无门店权限：SQL 追加 `1 = 0`，返回空结果。
- 字段编码命中 `exists` 配置且用户同时配置前端门店筛选：结果为前端筛选门店和权限门店的交集。
- 多个行级权限字段同时生效：字段编码命中 `exists` 配置的字段追加独立 `exists` 条件，未命中配置的字段保持原 `IN` 条件，所有条件之间为 `AND`。
- 城市权限兼容 DMG 的定制逻辑仍只作用于城市字段普通/权限过滤，不影响门店权限 exists。
- 回归普通筛选：普通 `include`、`exclude`、textarea、范围筛选生成 SQL 不变。

## 6. 风险与注意事项

- `exists` 方案依赖 Doris 侧权限表，如果同步延迟过大，会影响字段编码命中配置的字段权限实时性。
- 权限表必须控制重复数据，建议按 `user_name + field_code + dim_code + item_code` 去重。
- 如果 `item_code` 与事实表字段类型不一致，需要在同步表或 SQL 中统一类型，避免 Doris 隐式转换影响性能。
- 当前 `queryDataAuthByUser` 返回明细值，字段编码命中 `exists` 配置的字段应逐步替换为概要查询，避免 Java 侧继续加载大权限集合。
- 字段标识默认必须为关闭，避免上线后所有行级权限字段行为同时变化。
