# 本地文件缓存优化方案

## 1. 背景

当前 `LocalSqlResultCacheManager` 使用本地文件缓存 SQL 查询结果，缓存内容可能较大，不适合写入 Redis。公司 Redis 服务也不允许缓存大 key，因此不能将完整 `ResultDataSet` 放入 Redis。

现有实现存在几个问题：

- `getCache` 缓存未命中时没有同 key 并发控制，高并发下同一 SQL 会同时回源查询 DB。
- `addCache` 每次 `new Thread` 异步写文件，线程数量不可控。
- 文件写入直接覆盖目标文件，没有临时文件和原子 rename，读写并发时可能读到半文件。
- 当前 `LocalCacheManager.addCache` 通过 RMI 广播复写到多台机器，缓存结果较大时会放大网络和磁盘 IO。
- 本地文件缓存多实例之间共享能力弱，如果不复写，每台机器会各自回源查询。

## 2. 优化目标

- 大结果集仍然存本地文件，不进入 Redis。
- Redis 只存小元数据和小锁，避免大 key。
- 多实例之间可共享缓存结果。
- 不再通过 RMI 将大文件复写到所有机器。
- 高并发下同一 cacheKey 只允许少量请求回源，降低 Doris、Trino、MySQL 压力。
- 文件读写具备并发安全，不读半文件。

## 3. 总体方案

采用：

```text
本地文件存大结果
+ Redis 存小元数据
+ Redis 小锁防击穿
+ RMI 按固定 IP 远程读取文件
+ 原子写文件
+ 有界写线程池
```

核心模型：

```text
cacheKey
  -> Redis 元数据：serverIp、fileName、size、expireAt、status
  -> 文件内容：只存在 serverIp 对应机器的本地磁盘
  -> 远程读取：RMIServer.syncInvoke(FileSyncRmiService.class, serverIp, readOperation)
```

Redis 不保存完整查询结果，只保存缓存位置和状态。

## 4. Redis 元数据设计

建议 Redis key：

```text
sqlResultCache:{cacheKey}
```

value 示例：

```json
{
  "serverIp": "10.1.2.3",
  "fileName": "rs_xxx.txt",
  "size": 12345678,
  "expireAt": 1720000000000,
  "status": "ready"
}
```

字段说明：

- `serverIp`：缓存文件所在机器 IP。
- `fileName`：缓存文件名，只保存文件名，不保存任意路径。
- `size`：文件大小，用于大小控制和读取前校验。
- `expireAt`：过期时间戳。
- `status`：缓存状态，建议使用 `writing`、`ready`、`deleted`。

Redis TTL 与本地文件 TTL 保持一致。

## 5. 写缓存流程

查询完成后写缓存：

```text
1. 查询 DB 得到 ResultDataSet
2. 序列化为 JSON
3. 压缩，优先使用 Zstd 二进制压缩，不再 Base64 字符串化
4. 写入本机临时文件 cacheKey.tmp
5. flush/close 后原子 rename 为 cacheKey.txt
6. 写 Redis 元数据，status=ready
7. Redis TTL 设置为本地缓存 TTL
```

顺序必须是“文件写成功后再写 Redis 元数据”。不能先写 Redis，否则其他机器可能根据元数据读取到不存在或半写入的文件。

当前代码中：

```java
new Thread(() -> LocalCacheManager.addCache(cacheContent, cacheKey)).start();
```

建议改为有界线程池：

```text
固定写线程数：2 到 4
有界队列
同 cacheKey 正在写时，合并或丢弃重复写任务
```

## 6. 读缓存流程

读取缓存时：

```text
1. 根据 DataSourceType + SQL + user 生成 cacheKey
2. 优先读取本机 cacheKey.txt
3. 本机 miss 后查询 Redis 元数据
4. Redis 无元数据，返回 miss
5. Redis 有元数据，读取 serverIp
6. serverIp 是本机，读本机文件
7. serverIp 是其他机器，通过 RMI 固定 IP 读取远程文件
8. 读取压缩内容后，解压并反序列化为 ResultDataSet
9. 远程文件不存在、过期或读取失败时，忽略或删除 Redis 元数据，然后回源查询
```

固定 IP RMI 调用可复用现有方法：

```java
RMIServer.syncInvoke(FileSyncRmiService.class, serverIp, operation);
```

## 7. 防缓存击穿

使用 Redis 小锁控制同一个 `cacheKey` 的并发回源：

```text
SET sqlResultCache:lock:{cacheKey} {serverIp} NX EX 30
```

处理逻辑：

- 拿到锁的请求负责回源查询 DB，并写本地文件和 Redis 元数据。
- 没拿到锁的请求短暂等待，然后重新读取 Redis 元数据。
- 等待超时后可降级回源，避免请求长时间阻塞。
- 锁过期时间要覆盖大多数查询耗时，但不能过长。

Redis 只存锁和元数据，不存大结果，不违反大 key 限制。

## 8. 压缩与序列化优化

当前 `SSDUtil.compress` 实现如下：

```java
public static String compress(String str) {
    byte[] compressArray = Zstd.compress(str.getBytes());
    Base64 base64 = new Base64();
    String compressStr = base64.encodeAsString(compressArray);
    return compressStr;
}
```

对于大 `ResultDataSet` JSON，这种实现存在明显瓶颈：

- `str.getBytes()` 会复制一份完整原始字节数组，和原始 `String` 同时占用内存。
- `Zstd.compress` 会生成压缩后字节数组，进一步抬高峰值内存。
- Base64 会让压缩结果额外膨胀约 33%，写本地文件时没有必要。
- 压缩和 Base64 编码都是 CPU 密集操作，高并发时会抢占业务线程或写缓存线程 CPU。
- `str.getBytes()` 未指定字符集，存在平台默认编码差异，建议显式使用 UTF-8。
- 解压时一次性根据 `Zstd.decompressedSize` 申请完整解压数组，大文件可能导致 GC 抖动或 OOM。

针对本地文件缓存，建议不要继续使用“压缩后 Base64 字符串”的格式，而是改为直接写 Zstd 压缩二进制文件：

```text
ResultDataSet
-> JSON String
-> UTF-8 byte[]
-> Zstd compressed byte[]
-> 写入 cacheKey.tmp
-> 原子 rename 到 cacheKey.zst
```

读取时：

```text
读取 cacheKey.zst 二进制内容
-> Zstd 解压
-> UTF-8 String
-> JSON 反序列化为 ResultDataSet
```

如果短期为了兼容历史 `.txt` 缓存文件，可以支持两种格式：

```text
新格式：cacheKey.zst，Zstd 二进制
旧格式：cacheKey.txt，Base64 + Zstd 字符串
读取优先级：先读 .zst，读不到再兼容 .txt
```

建议增加压缩保护：

- 序列化后的 JSON 超过阈值时直接不缓存，避免压缩大对象拖垮 JVM。
- 压缩任务必须进入有界线程池，不能在请求线程或无界线程中执行。
- 记录 `rawSize`、`compressedSize`、`compressCostMs`，用于判断缓存是否值得保留。
- 压缩比过低时不缓存，例如压缩后仍大于原始大小的 80%。
- 解压前先检查文件大小和 Redis 元数据中的 `rawSize`，超过上限拒绝读取。

建议 Redis 元数据增加：

```json
{
  "serverIp": "10.1.2.3",
  "fileName": "rs_xxx.zst",
  "format": "zstd-binary",
  "rawSize": 104857600,
  "compressedSize": 12345678,
  "compressCostMs": 320,
  "expireAt": 1720000000000,
  "status": "ready"
}
```

这样可以在远程读取前判断文件大小、压缩格式和是否允许读取。

## 9. RMI 改造方案

当前 `RMIServer` 已支持固定 IP 调用：

```java
public static Object syncInvoke(Class<? extends IRMIService> serviceClass, String ip, Object param)
```

当前 `FileSyncRmiService` 只支持写入和删除，需要扩展读取能力。

建议扩展 `FileSyncOperation`：

```java
public static final String OPERATE_READ = "read";
```

`FileSyncRmiService.invoke` 增加读取逻辑：

```java
if (FileSyncOperation.OPERATE_READ.equalsIgnoreCase(operate)) {
    File file = new File(getSafeCacheFile(operation.getCacheKey()));
    if (!file.exists()) {
        return null;
    }
    return FileUtils.readFileToString(file, "UTF-8");
}
```

注意：远程读取接口不应允许调用方传完整任意路径。建议只传 `cacheKey` 或 `fileName`，服务端内部基于固定缓存目录拼接路径。

## 10. 替换现有多机复写

当前 `LocalCacheManager.addCache` 使用：

```java
RMIServer.syncInvoke(FileSyncRmiService.class, syncOperation);
```

这个方法会对 `BIUtil.getServerIPTable()` 中所有机器进行同步调用，适合小文件或配置同步，不适合大结果集缓存。

优化后改为：

```text
1. 只写当前机器本地文件
2. 不广播复写到其他机器
3. 写成功后注册 Redis 元数据
4. 其他机器根据 Redis 中的 serverIp 远程读取
```

这样可以避免大文件在多台机器间重复复制。

## 11. 文件并发安全

必须将直接覆盖写改为原子写：

```text
cacheKey.tmp
  -> 写入完成
  -> flush/close
  -> rename cacheKey.tmp 到 cacheKey.txt
```

读线程只读取正式文件 `cacheKey.txt`。

这样读线程要么读到旧完整文件，要么读到新完整文件，不会读到半文件。

## 12. 安全约束

远程读取文件必须加安全限制：

- RMI 入参只允许传 `cacheKey` 或安全文件名。
- 文件名只允许字母、数字、下划线、短横线，例如 `[a-zA-Z0-9_\\-]+`。
- 服务端内部拼接固定目录 `local.cache.file.dir`。
- 校验最终文件路径必须位于缓存目录下。
- 校验文件未过期。
- 校验文件大小不超过上限。
- RMI 服务仅允许内网调用，必要时增加签名或白名单。

避免把 RMI 文件读取能力变成任意文件读取漏洞。

## 13. 容量与清理

本地文件缓存需要增加容量控制：

- 单个缓存文件最大大小，例如 20MB、50MB，按业务配置。
- 单个原始 JSON 最大大小，超过阈值不进入压缩和缓存流程。
- 缓存目录总大小上限。
- 定时清理过期文件。
- 写缓存前检查剩余磁盘空间。
- 大于阈值的结果集不缓存。
- 远程读取前根据 Redis 元数据中的 `size` 判断是否允许读取。
- 远程读取前根据 Redis 元数据中的 `rawSize`、`compressedSize` 判断是否允许解压。

建议新增配置：

```properties
ssm.query.sql.local.cache.max.file.size.mb=50
ssm.query.sql.local.cache.max.raw.size.mb=200
ssm.query.sql.local.cache.max.dir.size.mb=10240
ssm.query.sql.local.cache.write.threads=4
ssm.query.sql.local.cache.lock.seconds=30
ssm.query.sql.local.cache.min.compress.ratio=0.8
```

## 14. 异常与降级

读取异常处理：

- Redis 无元数据：直接 miss。
- Redis 元数据过期：删除元数据并 miss。
- serverIp 不可达：忽略本次缓存，回源查询。
- 远程文件不存在：删除或覆盖 Redis 元数据，回源查询。
- 解压失败或 JSON 解析失败：删除本地文件和 Redis 元数据，回源查询。
- 文件过大：拒绝读取，回源查询或直接 miss。
- Redis 元数据中的 `rawSize` 超过上限：拒绝解压，回源查询或直接 miss。

写入异常处理：

- 本地文件写失败：不写 Redis 元数据。
- Redis 元数据写失败：本地文件可保留，但其他机器不可见。
- 原子 rename 失败：删除临时文件。
- 写线程池满：丢弃本次缓存写入，不影响查询主流程。
- 序列化结果过大、压缩耗时过长或压缩比过低：跳过本次缓存写入。

## 15. 改造步骤

### 阶段一：本地并发安全

- `addCache` 改为有界线程池。
- 写文件改为临时文件 + 原子 rename。
- 同 cacheKey 正在写时避免重复写。
- 增加单文件大小限制。
- 增加过期文件清理。

### 阶段二：压缩格式优化

- 新增 Zstd 二进制文件格式，避免 Base64 字符串化。
- 文件扩展名建议从 `.txt` 调整为 `.zst`。
- 短期兼容历史 `.txt` 缓存读取。
- Redis 元数据增加 `format`、`rawSize`、`compressedSize`、`compressCostMs`。
- 增加原始 JSON 大小上限、压缩后大小上限和压缩比阈值。

### 阶段三：Redis 元数据索引

- 新增缓存元数据对象。
- 查询完成后写 Redis 元数据。
- `getCache` 本地 miss 后读取 Redis 元数据。
- Redis 元数据 TTL 与本地 TTL 保持一致。

### 阶段四：RMI 固定 IP 远程读取

- 扩展 `FileSyncOperation.OPERATE_READ`。
- 扩展或新增 RMI 文件读取服务。
- 远程读取只允许按 cacheKey 读取固定缓存目录。
- `getCache` 根据 Redis 中的 serverIp 固定 IP 读取远程文件。

### 阶段五：防击穿

- 增加 Redis 小锁。
- 同 cacheKey miss 时只允许一个请求回源。
- 未拿到锁的请求等待并重试读缓存。
- 等待超时后降级回源。

### 阶段六：移除多机复写

- `LocalCacheManager.addCache` 不再广播调用所有机器。
- 文件只写本机。
- 依赖 Redis 元数据和固定 IP RMI 读取实现多实例共享。

## 16. 预期收益

- 大结果不进入 Redis，符合公司 Redis 大 key 限制。
- 不再将大文件复写到所有机器，降低磁盘和网络放大。
- 多实例之间仍可共享缓存。
- 同 SQL 高并发不会全部击穿到 Doris、Trino、MySQL。
- 文件读写更稳定，避免读到半文件导致解压失败。
- 写缓存线程数可控，不会因高并发创建大量线程。
- Zstd 二进制文件避免 Base64 膨胀，降低磁盘占用、网络传输和 CPU 编码成本。
- 可以复用现有 RMI 基础设施，整体侵入较小。

## 17. 需要重点关注的风险

- RMI 远程读取大文件仍会占用网络带宽和 JVM 内存，需要大小限制。
- Redis 元数据指向的机器不可达时，需要快速降级回源。
- 远程文件读取必须限制路径，避免任意文件读取。
- Redis 锁过期时间过短会导致重复回源，过长会导致等待时间增加。
- 本地缓存目录需要磁盘容量监控和清理机制。
- 读远程缓存比读本地缓存慢，热点缓存可考虑读取后在当前机器落一份本地副本，但要控制二次复制策略。
- 大字符串压缩和解压会产生明显 CPU、内存和 GC 压力，必须通过大小阈值、有界线程池、二进制压缩文件和监控指标控制。
