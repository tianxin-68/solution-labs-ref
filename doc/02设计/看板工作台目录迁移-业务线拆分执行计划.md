# 看板工作台目录迁移：业务线拆分执行计划

## 1. 背景与目标

门户（看板工作台）下部分目录当前挂在"老业务线"名下，业务侧要求按新业务线重新拆分：

| 老业务线 | 拆分为新业务线 |
| --- | --- |
| 保养 | 保养油液、保养配件 |
| 改装超市 | 超市改装、电子改装、电瓶车 |

目标：把门户下所有名称包含老业务线名称（"保养"/"改装超市"）的目录，整棵子树复制一份，复制出的每一份里把名称中的老业务线子串替换为对应新业务线名称，从而让每个新业务线各自拥有一套独立的目录/看板/共享空间/查询模板。

### 1.1 需求变更：超市改装拆分的命名冲突处理（2026-07-31 追加）

"超市改装运营分析"、"电子改装运营分析" 两个目录**已经存在**（非本次迁移产出，是历史已有目录）。为避免同名冲突、同时不破坏现有目录，本次迁移对"超市改装"拆分出的 3 份目标改为：

| 新业务线 | 复制来源 | 目标目录名称 | 说明 |
| --- | --- | --- | --- |
| 超市改装 | 老"超市改装运营分析"子树（**自身**） | 超市改装运营分析**-V2** | 目标名称已存在，新副本加 `-V2` 后缀区分 |
| 电子改装 | 已存在的"电子改装运营分析"子树（**自身**，**不是**从"超市改装运营分析"派生） | 电子改装运营分析**-V2** | 目标名称已存在，新副本加 `-V2` 后缀区分；**复制来源是它自己已有的内容**，不是把"超市改装"改名得到的 |
| 电瓶车 | 老"超市改装运营分析"子树 | 电瓶车运营分析 | 目标名称不存在，正常复制+改名，无需加后缀 |

> **2026-07-31 二次修正**："电子改装"目标的复制来源是**它自己已经存在的"电子改装运营分析"目录**（自我复制出一份 V2），不是从"超市改装运营分析"改名派生。也就是说"超市改装"拆分出的 3 份目标里，只有"电瓶车"是真正从"超市改装运营分析"改名派生的；"超市改装""电子改装"这两份都是**各自对自己已有目录的自我复制**（仅加 `-V2` 后缀，不做业务线子串替换）。"保养"拆分出的 2 份（保养油液、保养配件）目标名称当前都不存在，都是从"保养运营分析"做子串替换派生，不需要加后缀。

本篇只输出方案，不涉及代码实现。

## 2. 现状数据模型调研结论

### 2.1 门户目录树：`PortalMenu` / `ssm_portal_menu`

- 实体：`com.bi.queryer.ssm.portal.entity.PortalMenu`，mapper：`ssm.portal.menu.ibatis.xml`（namespace `ssm.portal.menu`）
- 关键字段：`menuId`(PK)、`portalId`、`menuName`（**纯文本，业务线信息只能靠子串识别，没有专门字段**）、`menuType`（对应 `PortalMenuType`）、`menuUrl`、`parentMenuId`（自关联树）、`contentRefId`（指向具体内容，如看板 id）、`sortId`、`isActive`、审计字段。
- **没有 `copy/clone` 已有实现**，只有 `move`（同级排序），迁移工具需要从零实现树复制。

### 2.2 目录类型枚举：`PortalMenuType`

```java
UNKNOWN, COMMON("普通目录"), ANALYSIS_TEMPLATE("看板"), TX_BI("txbi"),
SPACE_CTG("共享空间目录"), CONFIG_USED_SPACE_CTG("看板配置使用的共享空间目录"),
QUERY_TEMPLATE_CTG("查询模板目录"), PORTAL_CTG("门户目录"),
DYNAMIC_ANALYSIS_REPORT("专题分析报告"), DYNAMIC_ANALYSIS_REPORT_CTG("专题分析报告目录"),
AI_SKILL_CTG("技能集目录")
```

### 2.3 看板：`ssm_analysis_tpl_*`

- `AnalysisTemplateEntity`（表 `ssm_analysis_tpl_base`）：看板主体，`analysisTplId/analysisTplName/analysisTplOwner/...`，**没有 ctgId 字段**，目录挂载关系在 `PortalMenu.contentRefId` 上。
- `ssm_analysis_tpl_cfg_local` / `_prod`：草稿/线上配置 JSON（`analysisTplContent`），带版本号。
- `ssm_analysis_tpl_widget`：看板内每个图表组件，含 `queryTplId` + `queryTplViewIdMapping`（引用查询模板与其视图）。
- `ssm_analysis_tpl_widget_query_tpl_rel` / `ssm_analysis_tpl_query_tpl_rel`：看板↔查询模板依赖关系缓存表。
- `ssm_analysis_tpl_view`：看板级"页签/视图"（与查询模板视图是两个不同概念，注意不要混淆）。
- 已有的 `AnalysisTemplateService.copyWidgetConfigToNewCfg` / `copyAnalysisTplWidgetQueryTplRel` 只是同一个 `analysisTplId` 下草稿→线上版本拷贝，**不产生新 analysisTplId**，可作为"如何批量拷贝 widget/rel 行"的写法参考，但不能直接复用做跨看板克隆。

> **确认更新**：看板复制不是复用现成实现，而是**由本方案自己定义一个新接口**（下面 3.2 节的签名即为最终约定，不是占位）。

### 2.4 共享空间与查询模板：`ssd_query_template_*`

- "共享空间"不是独立实体，是 `QueryTemplateCategory`（表 `ssd_query_template_ctg`）里 `ctg_type = space` 的一个节点，子树下挂常规目录/模板。
- ACL：`ssd_query_template_space`（`TemplateSpaceEntity`：`space_ctg_id/owner_type/owner_id/owner_role`），`TemplateSpaceService` 目前只有 `saveSpace/editSpace/exitSpace`，**没有克隆空间的方法**。
- 查询模板：`TemplateEntity`（表 `ssd_query_template`，`tplId/ctgId/cfgId/...`，自带 `clone()` 做 JSON 浅拷贝），配置在 `ssd_query_template_cfg` / `_cfg_dtl`。
- 模板视图：`TemplateViewEntity`（表 `ssd_query_template_view`），与模板是 1:N。已有 `TemplateViewService.copyView(oldTplId, newTplId, excludeViewId, tplType)` 返回 `List<TemplateViewMapping>`（旧 viewId → 新 viewId），以及 `TemplateConfigService.saveAsTemplateAndView(...)`（"另存为"完整流程：新建模板 + copyView）——**这是本次迁移里"模板+视图复制"最贴近可复用的代码路径**。
- 可参考的树复制算法：`QueryTemplateCategoryService.shareCategoryToUser`——递归取子树 → clone 每个节点生成新 id → 用 源parent→源id 映射表 重建新树的 parentId → 批量插入 → 再逐个复制模板内容。该算法结构可直接套用，但它是"分享给用户"场景，不会拷贝 `ssd_query_template_space` 的 ACL 行，迁移时需要额外处理。

> **确认更新**：查询模板/视图的复制**必须是新接口，不能复用 `TemplateViewService.copyView` / `TemplateConfigService.saveAsTemplateAndView` 等老接口**（下面 3.3 节的签名即为最终约定）。共享空间目录树本身（`ssd_query_template_ctg` 节点）和 ACL（`ssd_query_template_space`）没有现成实现，继续由迁移工具自己复制。

### 2.5 无既有业务线枚举

代码库里没有任何"保养/超市改装/保养油液/保养配件/电子改装/电瓶车"相关的枚举或常量，也没有"看板工作台"对应的固定 `portalId`。这些都是纯业务数据，**需要先在生产/目标环境的 `ssm_portal_menu` 里查出实际的门户 id 和根目录 id**，不能假设成代码里的常量。

## 3. 迁移范围分类与处理策略

按 `menuType` 把门户目录节点分三类，处理方式不同：

### 3.1 纯目录复制（只复制目录节点，引用内容不复制）

`COMMON`、`PORTAL_CTG`、`DYNAMIC_ANALYSIS_REPORT`、`DYNAMIC_ANALYSIS_REPORT_CTG`、`AI_SKILL_CTG`、`TX_BI`

- 只在 `ssm_portal_menu` 里插入新行（新 `menuId`，`parentMenuId` 指向本次复制出的新父目录，`menuName` 按规则替换），`contentRefId` **保持指向原内容**（专题报告、TxBI 资源、AI 技能定义都不重复生成）。
- 效果：这些叶子节点在新老业务线目录下是"同一份内容的不同入口"，内容本身没有拆分诉求。

### 3.2 看板全量复制

`ANALYSIS_TEMPLATE`

> 已确认：由本方案定义一个新接口，入参固定为 3 个——看板 id、老业务线名称、新业务线名称，接口内部自行完成名称替换与内容克隆。

- 接口契约（最终约定，非占位）：

  ```java
  /**
   * 复制看板到新业务线。
   * @param analysisTplId 老看板 id
   * @param oldBizLine    老业务线名称（用于名称子串替换）
   * @param newBizLine    新业务线名称（替换后的目标名称片段）
   * @return 新 analysisTplId，以及看板内部 widget 对 queryTplId/viewId 的引用重映射结果
   */
  DashboardCopyResult copyDashboard(String analysisTplId, String oldBizLine, String newBizLine);
  ```

- 迁移工具职责：直接调用 `copyDashboard(老analysisTplId, oldBizLine, newBizLine)` → 用返回的新 `analysisTplId` 新建一条 `PortalMenu` 行（`menuType=analysis_template`，`contentRefId=新analysisTplId`，挂到 3.1 里对应的新父目录下）→ 把 `(old, new)` 写入第 5 节映射表。
- 假设：`copyDashboard` 内部会自行把 widget 的 `queryTplId`/`queryTplViewIdMapping` 重新指向"本批次新复制出的查询模板"（3.3 产出），迁移工具不需要再单独回填；若实现时发现该接口不具备这个能力，需要补一个参数把 3.3 的旧→新 tplId/viewId 映射传进去。

### 3.3 共享空间目录复制（含内部查询模板/视图）

`SPACE_CTG`、`CONFIG_USED_SPACE_CTG`

> 已确认：查询模板/视图的复制也由本方案**新建接口**，不复用 `TemplateViewService.copyView` / `TemplateConfigService.saveAsTemplateAndView`。共享空间目录树本身（`ssd_query_template_ctg` 节点）和 ACL（`ssd_query_template_space`）没有现成实现，继续由迁移工具自己复制（与看板接口保持同样的"id + 老业务线 + 新业务线"入参风格）。

- 接口契约（最终约定，非占位）：

  ```java
  /**
   * 复制单个查询模板（含其全部视图）到新业务线。
   * @param tplId      老查询模板 id
   * @param oldBizLine 老业务线名称
   * @param newBizLine 新业务线名称
   * @return 新 tplId，以及模板下所有视图的旧→新 viewId 映射
   */
  QueryTemplateCopyResult copyQueryTemplate(String tplId, String oldBizLine, String newBizLine);
  ```

- 迁移工具职责：
  1. 自行复制共享空间目录节点（`ssd_query_template_ctg`，新 `ctgId`，名称按规则替换）+ 复制 ACL（`ssd_query_template_space` 原样克隆到新 `space_ctg_id`）。
  2. 对该目录下每个查询模板调用 `copyQueryTemplate(tplId, oldBizLine, newBizLine)`，拿到旧→新 `tplId`/`viewId` 映射，新模板挂到第 1 步建好的新目录（`ctgId`）下。
  3. 新建对应的 `PortalMenu` 行（`menuType=space_ctg` 或 `config_used_space_ctg`），名称按规则替换。
  4. 把第 2 步返回的映射写入第 5 节映射表，供 3.2 回填看板 widget 引用使用。**执行顺序上共享空间/查询模板必须先于看板内容复制完成。**

## 4. 目录识别与命名替换规则

1. **匹配对象由 `MetricMigrateTarget` 显式指定复制来源，不再单纯靠子串扫描全树定位根节点**（1.1 节二次修正的直接原因：如果只按"名称含超市改装"扫描，找不到"电子改装运营分析"这个源）。每个目标携带一个显式的 `sourceRootName`：
   - 保养油液：`sourceRootName="保养运营分析"`
   - 保养配件：`sourceRootName="保养运营分析"`
   - 超市改装：`sourceRootName="超市改装运营分析"`
   - 电子改装：`sourceRootName="电子改装运营分析"`（**注意不是"超市改装运营分析"**）
   - 电瓶车：`sourceRootName="超市改装运营分析"`

   实际定位时，在指定 `portalId` 下按名称精确匹配 `sourceRootName` 找到复制根节点（而不是模糊子串匹配），避免匹配到无关的同名子串节点。
2. **只在匹配到的根节点处触发复制**：对其整棵子树做整体复制，不再单独处理子孙节点是否含关键字触发新一轮复制。
3. **复制份数**：`MetricMigrateTarget` 列表本身就是"一份配置=一次复制"，天然对应保养→2 份、超市改装拆分→3 份（其中 2 份的 `sourceRootName` 相同、1 份不同）。
4. **命名替换**：每个目标额外携带 `oldToken`/`newToken`（替换用的子串对）：
   - 跨业务线派生的目标（保养油液/保养配件/电瓶车）：`oldToken` 是老业务线名称（"保养"/"超市改装"），`newToken` 是新业务线名称，对子树内**所有**节点名称做子串替换。
   - 自我复制的目标（超市改装-V2、电子改装-V2）：`oldToken`/`newToken` 相同（等价于不替换），只在此基础上追加 `nameSuffix`。
5. **命名冲突后缀（`-V2`）**：见 1.1 节，"超市改装"、"电子改装" 两个目标各自的复制来源在门户里本来就是（或将会是）同名目录，所以都需要显式的 `nameSuffix="-V2"`；"电瓶车"、"保养油液"、"保养配件" 三个目标不需要后缀（`nameSuffix=""`）。已确认这是**本次迁移的一次性命名策略**，不做"自动探测重名并递增版本号"的通用机制——以后如果再遇到类似情况，同样通过人工在 `MetricMigrateTarget` 里配置 `sourceRootName`/`oldToken`/`newToken`/`nameSuffix` 解决。
6. 复制时同时递归覆盖 3.1/3.2/3.3 三类子节点各自的复制逻辑（一棵子树里可能混合了普通目录、看板、共享空间引用节点）。
7. **挂载位置**：所有新复制出的子树根节点，都挂在**其 `sourceRootName` 对应老目录所在的同一个 `parentMenuId`** 下（与来源目录同级），不改变父级结构。

### 4.1 "同名复用"规则（2026-07-31 追加确认，8-1 已扩大范围）

新增确认：**同一个业务线下不允许重名**，因此"如果按命名规则算出的新名称在目标范围内已经存在，则复用已存在对象的 id，不再重复创建"这条规则对**所有节点类型统一适用**——不再区分目录类与内容类：

- 目录/容器类：3.1 的 `COMMON`/`PORTAL_CTG`/`DYNAMIC_ANALYSIS_REPORT_CTG`/`AI_SKILL_CTG`，3.3 的 `ssd_query_template_ctg` 目录树节点、`SPACE_CTG`/`CONFIG_USED_SPACE_CTG` 菜单节点。
- 内容类：`DYNAMIC_ANALYSIS_REPORT`、`TX_BI`、`ANALYSIS_TEMPLATE`（看板）、查询模板本身（`ssd_query_template`）——**同名也复用**，不再无条件调用 3.2/3.3 的复制接口产出新对象。

- **判断依据**：
  - 目录/容器类：在目标父级 `parentMenuId`（或 `ctg_parent_id`）下，按 `(menuName, menuType)` 查是否已存在同名同类型节点。
  - 看板：在目标业务线归属的门户目录范围内，按 `analysisTplName` 查是否已存在同名看板（`menuType=analysis_template`）。
  - 查询模板：在目标业务线归属的共享空间/查询模板目录（`ctgId`）下，按 `tplName` 查是否已存在同名模板。
  - 命中 → 复用其 id（不调用复制接口/不插入新行），把 `(oldId → 已存在的newId)` 写入第 5 节映射表，`isReused=true`。
  - 未命中 → 正常创建（插入目录行 / 调用 3.2 的 `copyDashboard` / 调用 3.3 的 `copyQueryTemplate`），把 `(oldId → 新id)` 写入映射表，`isReused=false`。
- **与 `-V2` 后缀规则的关系不变**："超市改装""电子改装"两个目标之所以要加 `-V2` 后缀，正是因为不想复用已存在的同名目录（希望产出独立新副本）；加了后缀后，新名称在目标范围内自然查不到同名对象，于是走正常创建分支，不会触发本节的复用逻辑。**是否复用统一由"算出来的目标名称在目标范围内是否已存在"决定**，`nameSuffix` 是业务方主动避开复用的手段，对目录、看板、查询模板同样适用。
- **为什么"每一次复制都要记录映射"（即使是复用分支）**：子节点的新父级 id（`newParentMenuId`/新 `ctgId`）来自"父节点映射记录里的 newId"；看板 widget 要回填的 `queryTplId`/`viewId` 同样来自查询模板的映射记录。如果复用分支不记录映射，下游节点在增量执行时就找不到正确的新 id，会导致整棵子树/看板引用挂载错位。所以**无论是新创建还是复用已有对象，都必须写入第 5 节的映射表**，这是第 6 节增量执行能正确工作的前提。

## 5. ID 映射记录方案

需要记录三类映射：目录（`ssm_portal_menu.menuId`）、看板（`analysisTplId`）、查询模板视图（`viewId`，连带 `tplId`、共享空间 `ctgId`）。

建议新增一张迁移映射表（迁移过程审计与回溯用），字段参考：

| 字段 | 说明 |
| --- | --- |
| id | 主键 |
| objectType | portal_menu / analysis_tpl / query_tpl / query_tpl_view / space_ctg |
| oldId / oldName | 老对象 id、名称 |
| newId / newName | 新对象 id、名称 |
| oldBizLine / newBizLine | 老/新业务线 |
| portalId | 所属门户 |
| isReused | 该 newId 是否为"同名复用"得到的已存在节点（true）还是本次新插入（false），见 4.1 节 |
| createdBy / createdTime | 审计字段 |

该表可以直接对应此前已建好的空包 `com.bi.queryer.ssm.migrate.bizsplit.model` 里的 `MetricMigrateMappingEntity`。

> **增量执行的关键依据**：这张映射表同时也是"哪些老节点已经迁移过"的唯一判断依据——每次运行都以 `(objectType, oldId, newBizLine)` 是否已存在映射记录，来判断该老节点在该目标业务线下是否需要（重新）复制，见第 6 节。

## 6. 执行流程：直接写正式表 + 支持增量执行

已确认：**不采用影子表/预演/提交的两阶段模式，直接写正式表**；同时接口要**支持增量执行**——后续老业务线目录下新增了目录/看板/模板，重新调用同一个接口即可只把"新增部分"同步过去，已经同步过的节点不会重复复制。

### 6.1 幂等判断依据（两层校验）

对老树里的每一个节点（目录/看板/查询模板/视图），在处理前依次做两层检查：

1. **映射表检查**（本工具自己的记账）：若 `(objectType, oldId, newBizLine)` 在第 5 节映射表里**已存在**记录 → 跳过（已同步过，包括之前"复用已有节点"产生的记录）。
2. **同名复用检查**（4.1 节，**所有节点类型统一适用**，含目录、看板、查询模板）：映射表里没有记录时，按目标名称在目标范围内查是否已有同名同类型对象——有则复用其 id，没有则正常创建（插入目录行 / 调用看板复制接口 / 调用查询模板复制接口）；无论哪种结果都要写入映射表（见 4.1 节末尾说明）。

由此，"首次全量迁移"和"后续增量迁移"是**同一套逻辑**，不需要区分两种模式：第一次运行时映射表是空的，等价于把整棵老树当作"全部都是新节点"处理一遍（每个节点仍会先过一遍同名复用检查）。

### 6.2 执行步骤

```

1. 对每个 MetricMigrateTarget，先判断 sourceRootName 是否等于其 portalId 对应门户自身的名称：
   - 是 → 走"整门户复制"（新建/复用 ssm_portal 行 + 复制门户下所有顶层目录，门户名称按根节点规则计算）。

      - 3.2 类（看板）：调用 3.2 节新定义的 `copyDashboard` 接口，用上一步产出的查询模板映射回填 queryTplId/viewId，在正式表新建 PortalMenu 行挂载。
```

## 7. 校验方案

复制完成后建议校验：

1. 每个新业务线目录子树的节点数量，应与对应老业务线子树节点数量一致（一一对应，除去 `contentRefId` 共享的纯目录节点内容层面不做数量比较）。
2. 每个新看板的 widget 数、`queryTplId` 引用数，应与老看板一致，且新看板引用的 `queryTplId` 全部落在"本目标业务线下的查询模板"集合内（新建的或同名复用到的都算，唯独不能出现仍引用老业务线模板 id 的漏改情况）。
3. 每个新共享空间的 ACL 行数（`ssd_query_template_space`）应与老空间一致。
4. 名称抽查：新子树内所有节点名称中不应再包含老业务线关键字（"超市改装-V2"/"电子改装-V2" 两份是替换后加了后缀，本身也不应再含"超市改装"这个老业务线关键字本体，因为它已被替换为对应新业务线名称+后缀）。
5. 映射表（第5节）行数应与实际"新插入 + 复用"对象数之和一致（`isReused=false` 的行数 = 正式表新插入行数），不多不少。
6. **增量执行校验**：对已经迁移过的老节点重新触发一次执行，映射表和正式表都不应产生新增/重复记录（幂等性验证）。
7. **同名复用校验**：对 4.1 节命中复用分支的对象（目录/看板/查询模板），抽查其映射记录 `isReused=true`，且下游引用（子节点的 `parentMenuId`、看板 widget 的 `queryTplId`）确实指向该复用对象的 id（而不是又新建了一个同名对象）。
