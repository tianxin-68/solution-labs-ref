# 日方差（var_pop_by_d）系统重构方案

## 1. 结论

本次重构建议统一采用“按日预聚合 + 二次聚合”的模型，日均值不再根据原始聚合表达式是否包含 `count(distinct)` 来选择不同执行路径。

也就是说，牺牲一部分普通指标日均的性能优化，换取逻辑一致性、实现清晰度和后续扩展能力。

统一后的核心口径：

```text
日类二次聚合 = 先按日把明细数据按原始聚合方式算出 daily_value，再对 daily_value 做二次计算
```

对应关系：

| 聚合方式 | code | 第一阶段 | 第二阶段 | 日期参与口径 |
| --- | --- | --- | --- | --- |
| 多日均值 | `avg_by_d` | 按日原始聚合得到 `daily_value` | `sum(daily_value) / calendar_days` | 自然日，保持历史口径 |
| 非空日均值 | `avg_by_d_r` | 按日原始聚合得到 `daily_value` | `avg(daily_value)` 或 `sum(daily_value) / count(distinct day)` | 非空日 |
| 日方差 | `var_pop_by_d` | 按日原始聚合得到 `daily_value` | `var_pop(daily_value)` | 非空日 |

重点变化：

```text
旧逻辑：
普通日均：外层聚合值 / 天数
count(distinct) 日均：先按日去重，再外层除天数
日方差：无历史逻辑

新逻辑：
所有日均、非空日均、日方差：统一先按日聚合，再二次计算
```

## 2. 为什么建议去掉 count(distinct) 执行分叉

历史日均中存在一个性能优化：

```text
如果原始聚合不包含 count(distinct)，则不先按日聚合，直接最终聚合值 / 天数。
如果原始聚合包含 count(distinct)，则先按日聚合，再除以天数。
```

这个优化对 `sum`、`count` 等可加指标是成立的，例如：

```text
sum(daily_sum(amount)) / days
等价于
sum(amount) / days
```

但它带来几个问题：

1. 日均值有两套 SQL 执行路径，理解成本高。
2. `Avg_By_Day` 判断散落在 wrapper、aggregator、analysis、LOD、UI normalizer 中。
3. 新增 `var_pop_by_d` 时，方差必须依赖每日值序列，不能复用“最终聚合值 / 天数”的 shortcut。
4. 如果继续保留日均 shortcut，系统会同时存在“日均 shortcut”和“日方差二阶段聚合”两套模型，后续扩展日标准差、日最大值、日分位数时还会继续分叉。
5. 计算字段、LOD、总计、同环比等场景下，分叉会放大复杂度和遗漏风险。

因此，本次建议将 `count(distinct)` 判断从核心 SQL 构建逻辑中移除，让日均值也统一走日预聚合模型。

代价：普通日均查询会多一层按日 group by，长时间范围、多维度、大数据量场景可能比旧逻辑慢。

收益：模型清晰、代码统一、日方差实现正确、后续扩展成本低。

## 3. 统一后的 SQL 模型

### 3.1 多日均值 `avg_by_d`

原始指标：`sum(amount)`。

统一后 SQL 结构：

```sql
select
    final_dims,
    sum(daily_value) * 1.0000 / calendar_days as amount_avg_by_d
from (
    select
        final_dims,
        min_date_granularity_code,
        sum(amount) as daily_value
    from base_data
    where ...
    group by final_dims, min_date_granularity_code
) d
group by final_dims
```

如果原始指标是 `count(distinct user_id)`：

```sql
select
    final_dims,
    sum(daily_value) * 1.0000 / calendar_days as user_cnt_avg_by_d
from (
    select
        final_dims,
        min_date_granularity_code,
        count(distinct user_id) as daily_value
    from base_data
    where ...
    group by final_dims, min_date_granularity_code
) d
group by final_dims
```

两者只差第一阶段的原始聚合表达式，外层二次计算逻辑一致。

### 3.2 非空日均值 `avg_by_d_r`

```sql
select
    final_dims,
    avg(daily_value) as amount_avg_by_d_r
from (
    select
        final_dims,
        min_date_granularity_code,
        sum(amount) as daily_value
    from base_data
    where ...
    group by final_dims, min_date_granularity_code
) d
group by final_dims
```

或者保留等价表达：

```sql
sum(daily_value) * 1.0000 / count(distinct min_date_granularity_code)
```

建议优先使用 `avg(daily_value)`，表达更直观；如果现有 try-catch、空值处理、Doris/Trino 兼容性要求更适合除法表达，也可以保留除法表达。

### 3.3 日方差 `var_pop_by_d`

```sql
select
    final_dims,
    var_pop(daily_value) as amount_var_pop_by_d
from (
    select
        final_dims,
        min_date_granularity_code,
        sum(amount) as daily_value
    from base_data
    where ...
    group by final_dims, min_date_granularity_code
) d
group by final_dims
```

如果原始指标是 `count(distinct user_id)`：

```sql
select
    final_dims,
    var_pop(daily_value) as user_cnt_var_pop_by_d
from (
    select
        final_dims,
        min_date_granularity_code,
        count(distinct user_id) as daily_value
    from base_data
    where ...
    group by final_dims, min_date_granularity_code
) d
group by final_dims
```

日方差不能优化成最终聚合值直接计算，因为方差依赖每日值分布。

## 4. 重构设计

### 4.1 聚合类型能力化

修改 `AggExpressionType`，新增：

```java
Var_Pop_By_Day("var_pop_by_d", "日方差", "日方差", "")
```

新增能力方法：

```java
public boolean isByDayReAggregation();
public boolean isAvgByDay();
public boolean isCalendarDayAvg();
public boolean isRealDayAvg();
public boolean isDailyVariance();
public String getByDaySecondAggFunction();
public static AggExpressionType resolveByDayAggBySuffix(String idOrCode);
public static String stripByDayAggSuffix(String idOrCode);
public static String appendByDayAggSuffix(String idOrCode, AggExpressionType aggType);
public static List<AggExpressionType> getByDayReAggregationTypes();
```

语义：

```java
isByDayReAggregation()
// avg_by_d、avg_by_d_r、var_pop_by_d 均返回 true

isAvgByDay()
// 仅 avg_by_d、avg_by_d_r 返回 true，用于兼容标题、格式化等日均专属逻辑
```

注意：`var_pop_by_d` 是 ByDay 聚合，但不是日均。不要复用日均标题和 `AVG_FORMAT_SUFFIX`。

### 4.2 新增日类二次聚合策略

建议新增：

```java
com.bi.queryer.ssm.engine.aggregation.day.DayReAggregationSpec
com.bi.queryer.ssm.engine.aggregation.day.DayReAggregationSpecFactory
```

`DayReAggregationSpec` 负责描述二阶段聚合行为：

```java
class DayReAggregationSpec {
    private AggExpressionType aggType;
    private DayParticipationMode dayMode;
    private String secondAggFunction;
    private boolean calendarDayDivisor;
    private boolean nonEmptyDayOnly;
}
```

`DayParticipationMode`：

```java
CALENDAR_DAY     // avg_by_d，自然日参与，保持历史口径
NON_EMPTY_DAY    // avg_by_d_r、var_pop_by_d，仅有数据日参与
```

映射关系：

```java
avg_by_d:
    dayMode = CALENDAR_DAY
    second expression = sum(daily_value) / calendar_days

avg_by_d_r:
    dayMode = NON_EMPTY_DAY
    second expression = avg(daily_value)

var_pop_by_d:
    dayMode = NON_EMPTY_DAY
    second expression = var_pop(daily_value)
```

### 4.3 删除日均 count(distinct) 执行分叉

旧逻辑中类似下面的判断需要下沉或删除：

```java
if (BIUtil.isCountDistinctAggExpression(aggExpression)) {
    if (aggType == Avg_By_Day || aggType == Avg_By_Day_Real) {
        distinctFields.add(f);
    }
}
```

新逻辑改为：

```java
if (aggType.isByDayReAggregation()) {
    byDayReAggFields.add(f);
} else {
    commonFields.add(f);
}
```

也就是说：是否需要日预聚合只由前端选择的聚合方式决定，不再由原始聚合表达式是否包含 `count(distinct)` 决定。

重命名建议：

```text
distinctFields -> byDayReAggFields 或 dailyPreAggFields
buildDistinctAggSql -> buildDailyPreAggSql
SingleModelBuilderAvgWrapper -> SingleModelBuilderByDayReAggWrapper
DefaultDataSourceSqlBuilderAvgWrapper -> DefaultDataSourceSqlBuilderByDayReAggWrapper
AnalysisSingleModelSqlBuilderAvgWrapper -> AnalysisSingleModelSqlBuilderByDayReAggWrapper
LodSingleModelSqlBuilderAvgWrapper -> LodSingleModelSqlBuilderByDayReAggWrapper
AnalysisSingleModelAvgTotalSqlBuilder -> AnalysisSingleModelByDayReAggTotalSqlBuilder
```

为降低一次性改名风险，可以保留旧类名，内部继承或委托新类。

## 5. SQL 构建层改造

### 5.1 单模型 SQL 构建

`SingleModelBuilderAvgWrapper` 当前职责是为了日均 count distinct 场景拆分普通指标和去重日均指标。

改造后职责变为：

```text
拆分普通指标和所有 ByDay 聚合指标
```

处理逻辑：

1. 扫描 result measure。
2. 如果 `AggExpressionType.get(field.getAggExpressionType()).isByDayReAggregation()`，加入 `byDayReAggFields`。
3. 普通指标加入 `commonFields`。
4. 对 `byDayReAggFields` 构建日预聚合 SQL。
5. 外层按最终维度做二次聚合。
6. 如普通指标和 ByDay 指标同时存在，继续使用当前 full join 或等价拼接策略。

### 5.2 数据源 SQL 包装

`DefaultDataSourceSqlBuilderAvgWrapper` 当前只在“有 count distinct 且日均”时包装。

改造后：

```text
只要存在 ByDay 聚合字段，就需要为这些字段提供日粒度预聚合结果。
```

判断逻辑：

```java
boolean hasByDayReAgg = resultFields.stream()
    .filter(QueryField::isMeasure)
    .anyMatch(f -> AggExpressionType.get(f.getAggExpressionType()).isByDayReAggregation());
```

不再判断：

```java
BIUtil.isCountDistinctAggExpression(aggExpression)
```

### 5.3 聚合器职责

建议拆成两个聚合器职责：

```text
FirstStageAggregator：生成每日值 daily_value 的原始聚合表达式
SecondStageAggregator：基于 daily_value 生成最终表达式
```

第一阶段：

```java
DefaultAggregator.aggregate(field)
```

即继续复用字段元数据中的原始聚合方式。

第二阶段根据 `DayReAggregationSpec`：

```java
avg_by_d:
    sum(daily_value) * 1.0000 / calendar_days

avg_by_d_r:
    avg(daily_value)

var_pop_by_d:
    var_pop(daily_value)
```

`AggregatorFactory` 不再 special case 日均：

```java
if (aggType.isByDayReAggregation()) {
    return new ByDaySecondStageAggregator(cxt, DayReAggregationSpecFactory.get(aggType));
}
return new DefaultAggregator(cxt);
```

## 6. 日均历史口径如何保持

统一按日预聚合后，仍需保持日均口径不变。

### 6.1 `avg_by_d` 自然日天数

`avg_by_d` 的分母不能改成非空日数量，仍然使用历史的自然日天数逻辑：

- 日期汇总查询：使用过滤日期范围天数。
- 日粒度且有总计：总计使用过滤日期范围天数。
- 周/月/季/年：沿用 `bi_get_month_days`、`bi_get_quarter_days`、`bi_get_year_days` 等历史逻辑。
- 业务日历：沿用 `PromotionManager.getPromotionTotalDays`、`PROMOTION_DURATION_DAYS_CODE` 等逻辑。
- 分析对比：沿用 `AnalysisAverageByDayAggregator` 中自定义对比、月环比、剔除未到达日期的逻辑。

因此，可以把 `AverageByDayAggregator` 中“分母天数计算”抽出来复用，而不是复用它的“最终聚合值直接除天数”执行方式。

### 6.2 `avg_by_d_r` 非空日口径

非空日均的分母是有数据日期数量。统一二阶段后可以直接：

```sql
avg(daily_value)
```

如果需要和历史 null/try-catch 表现完全一致，也可以使用：

```sql
sum(daily_value) * 1.0000 / count(distinct min_date_granularity_code)
```

建议先选择与历史结果最一致的表达式，再逐步清理。

## 9. 分阶段实施建议

### 阶段一：能力收口

1. 新增 `AggExpressionType.Var_Pop_By_Day`。
2. 新增 ByDay 能力方法和后缀工具。
3. 替换 UI、权限、LLM、目标值等非 SQL 主链路中的后缀硬编码。
4. `MeasureFieldAutoExtender` 支持 `var_pop_by_d`。

### 阶段二：统一日预聚合 SQL

1. 新增 `DayReAggregationSpec`。
2. 新增或改造 `ByDayReAggWrapper`。
3. `avg_by_d`、`avg_by_d_r`、`var_pop_by_d` 全部走日预聚合。
4. 删除 wrapper 中基于 `count(distinct)` 的是否包装判断。
5. 保持 `avg_by_d` 的自然日分母计算逻辑。

### 阶段三：分析、总计、LOD 接入

1. 分析场景接入统一 ByDay wrapper。
2. 总计场景按聚合类型选择二次表达式。
3. LOD 场景确保第一阶段 group by 包含 LOD 维度和最细日期。
4. 计算字段确保先得到每日原子指标值，再做每日表达式，最后二次聚合。

### 阶段四：清理命名和兼容类

1. 将 `*AvgWrapper` 逐步重命名为 `*ByDayReAggWrapper`。
2. 老类名保留为兼容入口，避免一次性改动过大。
3. 清理 `distinctFields`、`buildDistinctAggSql` 等误导性命名。

8. 总计场景中的 `avg_by_d` 和 `var_pop_by_d`。

## 11. 风险与处理

| 风险 | 说明 | 处理建议 |
| --- | --- | --- |
| 普通日均性能下降 | 去掉 shortcut 后多一层按日 group by | 接受本次性能牺牲；必要时后续以开关恢复优化。 |
| 日均历史结果变化 | 统一二阶段后表达式变化 | 重点回归自然日分母、非空日分母、业务日历、总计。 |
| 总计场景复杂 | grouping sets 与日预聚合叠加 | 总计单独建 SQL 快照，避免把方差误写成除天数。 |
| LOD 聚合层级错误 | LOD 已有聚合维度 | 第一阶段必须包含 LOD 维度 + 最细日期。 |
| 计算字段口径错误 | 不能先全周期算表达式再方差 | 每日先算原子聚合和表达式，再二次聚合。 |
| 格式展示误导 | 日方差不是日均 | `isAvgByDay()` 和 `isByDayReAggregation()` 必须区分。 |

## 12. 最终建议

本次既然可以接受一定性能牺牲，建议明确删除日均中“是否包含 count(distinct)”的执行分叉。

最终模型保持一句话：

```text
所有按日类聚合都先得到 daily_value，再做二次计算。
```

这样 `avg_by_d`、`avg_by_d_r`、`var_pop_by_d` 在 SQL 构建层共享同一套骨架，只在二次表达式和日期分母策略上不同。代码会比保留历史 shortcut 更清晰，也更适合长期迭代。
